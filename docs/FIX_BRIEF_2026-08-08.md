## 2. How to work — rules from the project owner

- **Treat each fix as its own reviewed, separate change** — not one
  giant batch commit. One commit (or a small tightly-related group) per
  finding, with a commit message that names which finding it addresses.
  This makes each change independently reviewable and revertable if one
  turns out to be wrong, which matters because this is real financial
  data for a real business in daily active use.
- **This is live production data in active daily use.** Don't do
  anything destructive to the database directly. Every finding's fix is
  a *code* change (validation logic, matching heuristics, imports) — none
  of them require a data migration. If you find while working that one
  actually does need a data change, stop and treat that specifically as
  its own careful, previewed-before-run step (see how
  `supabase/migrations/20260808024900_dedupe_shifted_date_tiller_transactions.sql`
  was written: a commented-out preview SELECT before any destructive
  statement), not something to run blind.
- **After code changes, both a git push AND a Vercel production deploy
  are required** — per `HANDOFF.md` §5.8/§10, pushing to GitHub alone
  does not deploy `gm-money-web`. Deploy from `gm-money-web/`:
  `npx vercel --prod` (or the `mcp__Vercel__deploy_to_vercel` tool if
  available in your session). Confirm which the owner wants before your
  first deploy if it isn't already clear from your instructions — but a
  code fix that's committed-but-never-deployed isn't actually fixed from
  the owner's perspective, so don't stop at just pushing.
- **Verify against production data where reasonable**, the same way the
  audit did (read-only `SELECT`s via the Supabase MCP connector against
  project `qptipjjribhwjjakmwjx`, schema `gm_money` — see
  `docs/AUDIT_BRIEF.md` §6 for access notes). E.g. after fixing C1's
  match heuristic, it's worth re-running the audit's verification query
  to confirm real match candidates still look sane post-fix, not just
  that the code compiles.
- **Don't expand scope.** Fix what's described; don't refactor
  surrounding code, don't "while I'm in here" clean up unrelated things,
  don't add new features. If a fix genuinely requires a larger change
  than the finding implies, do the minimal version and note in the
  commit/PR why.
- Standard repo git hygiene applies: work on a feature branch, don't
  force-push, don't skip hooks.

## 3. Findings to fix, with concrete guidance

Full detail for every item below is in `docs/AUDIT_FINDINGS_2026-08-08.md`
— this section is a condensed pointer to each, not a replacement for
reading the full writeup before touching the code.

### Critical

**C1 — `lib/register.ts`'s dedupe heuristic can hide a real bank
transaction and skew the running balance.**
Fix both parts described in the findings doc's "suggested fix":
1. Tighten `looksLikeSameMerchant()` / `normalizedWords()` — add a
   stopword list (at minimum: "the", "and", "for", "pay", "vis", "pos",
   "debit", "card", "purchase", "online" — check real Tiller
   description text in production for other near-universal tokens
   before finalizing the list) and/or raise the minimum word length.
2. More importantly: stop treating an unconfirmed heuristic match the
   same as a confirmed one for balance purposes. A heuristic candidate
   should still surface as a "possible match" suggestion on the manual
   entry, but the candidate bank row should remain in `visible` (its
   own normal Register line) and included in `clearedSum` until a user
   explicitly confirms it via `matchToBank`. Only an explicit
   `transaction_matches` row should ever remove a bank row from
   `visible`/`clearedSum`. This likely means restructuring `dedupe()`'s
   return shape somewhat — `candidateByManualId` already exists for the
   UI hint, so the display logic mostly just needs to stop *also*
   hiding the bank row for unconfirmed candidates.

**C2 — `/api/tiller-sync`'s date-drift fix can merge two distinct
transactions.**
The findings doc's suggested fix is deliberately conservative — narrow
the auto-merge condition so a same-account+description+amount match
within the window is only treated as a date-drift correction when it's
unambiguous, and let genuinely ambiguous cases fall back to the
exact-key upsert (which will insert a second row — a known-acceptable
outcome, since that's the pre-fix behavior for a real duplicate-amount
case and is far less harmful than silently deleting one of two real
transactions). Concretely: consider requiring the "nearby" match to be
unique in the window (if `nearby.length > 1` after the description
filter, treat none of them as a confident match and fall back to
upsert) as a first-pass improvement — re-verify against production data
that this doesn't reintroduce the original date-drift-duplicate bug for
the common single-real-transaction case.

### High

**H1 — manual-entry sign validation blocks legitimate refunds.**
In `app/entry/actions.ts` and `app/register/actions.ts`, relax
`Math.sign(amount) !== expectedSign` from a hard rejection to something
that allows the documented refund-on-expense-category case. Simplest
correct fix matching `CLAUDE.md`'s actual rule: drop the sign check
entirely for manual entries too (matching how `app/review/actions.ts`
already correctly handles bank-fed transactions) — category type should
classify the transaction for totals/charts, not constrain the sign.
If the owner wants to keep some guardrail against genuine typos, a
confirmation step (not a hard block) is the safer middle ground — but
confirm which behavior is wanted before choosing between "no check" and
"soft-confirm," since this changes user-facing UX, not just validation
logic.

**H2 — dead `createSubcategory`/`createCategory` in
`app/settings/actions.ts`.**
Simplest fix: delete both functions from that file (confirmed unused —
re-verify with a repo-wide grep for imports from `@/app/settings/actions`
before deleting, in case something changed since the audit). If Settings
is meant to grow its own category management UI later, that's a
separate, new feature request — don't build it as part of this fix,
just remove the landmine.

### Medium

**M1 — `CUTOFF_DATE` duplicated across 4 files.**
Export `CUTOFF_DATE` from `lib/dashboard.ts` (already done) and replace
the independent literals in `lib/register.ts`, `lib/review.ts`, and
`app/api/tiller-sync/route.ts` with an import from `@/lib/dashboard`.
Watch for import-cycle issues — `lib/dashboard.ts` imports from
`lib/register.ts` already (`computeAdjustedAccountBalance`), so
`lib/register.ts` importing `CUTOFF_DATE` back from `lib/dashboard.ts`
would create a cycle. If that's a real problem, move `CUTOFF_DATE` to
its own small module (e.g. `lib/constants.ts`) that all four files
import from instead, and re-export it from `lib/dashboard.ts` for
backward compatibility with `app/page.tsx`'s existing import.

**M2 — residual `Promise.all` in `lib/dashboard.ts:168-182`.**
Change `pendingReviewCount`/`unclearedCount` from `Promise.all` to
sequential `await`s, matching the pattern already used elsewhere in the
same file and in `lib/register.ts`.

**M3 — non-constant-time secret comparisons.**
In both `app/api/tiller-sync/route.ts` and `app/api/cron/route.ts`,
replace `provided !== SHARED_SECRET` with a constant-time comparison.
Web Crypto is available in both runtimes (per `lib/session.ts`'s own
comment about Edge + Node both exposing `crypto.subtle`) — a simple
correct approach: hash both `provided` and the real secret with SHA-256
via `crypto.subtle.digest` and compare the resulting byte arrays with a
fixed-time loop, or use a small manual constant-time string-compare
helper. Keep it simple; this isn't a case that needs a dependency.

**M4 — no login rate-limiting; no password reset.**
Two separable pieces — treat as two commits:
1. Rate-limiting: add an attempt counter in `app/login/actions.ts`,
   e.g. a `login_attempts` table (or reuse an existing table) keyed by
   normalized email, incremented on failure, checked before attempting
   `bcrypt.compare`, with a short lockout window after N failures.
   Needs a small migration (new table or columns) — write it with a
   preview-first pattern per the rules above, and it needs a DB schema
   change, so flag that clearly in the commit/PR description.
2. Password reset: this is a bigger feature (needs an email-sending
   path, which per `HANDOFF.md` §4 doesn't exist yet — "notification
   digest emailing" has prefs UI but no provider wired up). Don't build
   this speculatively; note in your summary that it's blocked on the
   same missing email-provider decision as notification digests, and
   leave it for a dedicated pass once that's resolved.

**M5 — `matchToBank` doesn't re-validate account/amount.**
In `app/register/actions.ts`'s `matchToBank`, extend the initial
`select` to also fetch `account_id` and `amount` for both rows, and
add an explicit check that `manualRow.account_id === bankRow.account_id`
and `manualRow.amount === bankRow.amount` before inserting into
`transaction_matches`. Return a clear `ok: false` error if they
disagree.

**M6 — migration match-repoint logic gap.**
This finding is about a *migration script* that already ran once and
(per the audit's verification) produced no actual bad data. No fix
needed against production data. If you want to harden the script itself
for defensive-correctness in case a similar cleanup is ever needed
again, that's optional/low-priority — note it rather than spending real
effort here unless asked.

### Low

**L1 — unsanitized bank text in the AI advisor's LLM context.**
Owner-acknowledged as low-impact (advisory-only output). Optional:
strip/escape obviously suspicious patterns from `description` fields
before they enter `buildBusinessContext()`'s JSON, but this is
genuinely optional — don't spend significant effort here unless asked.

**L2 — `processDueScheduledTransactions()` check-then-insert race.**
Add a real unique constraint (migration needed — preview-first pattern
again) on `(business_id, schedule_id, transaction_date)` for rows where
`schedule_id is not null`, and change the insert to tolerate a conflict
(catch the unique-violation error code and treat it as "already
created" rather than propagating it as a hard failure).

**L3 — `/setup` TOCTOU on first-owner creation.**
Lowest priority in this list — single-tenant app, narrow window, only
exploitable before any account exists. If addressed, the cleanest fix
is a unique partial index or a small advisory-lock-style guard around
`createAppUser` when `role = 'owner'` and no owner exists yet; not worth
more than a small amount of effort.
